The preview lets you see a component on every target at once while you work on it. Think of a button you restyle in React and only later find too narrow in Svelte, a prop you rename that Angular no longer reads, or an agent asked for a screenshot of a card in seven frameworks that opens seven apps to take it.

`unframework preview` starts one dev server per target your `unframework.config.ts` names, and a page that shows the selection in one labelled frame per target. Pick an example or a component on the left, and change a component's props with the controls above the frames: every target renders the same thing with the same props.

This page walks you through it. We'll look at:

- **Running it** with `unframework preview`.
- **What it shows:** your examples and your components.
- **Controls:** the props the preview can set.
- **How it works:** the servers, the frames and what it writes.

## Run it

`unframework preview` comes with `@uxfront/unframework`, and needs `@unframework.dev/visual` and `vite` in your project, beside what [`unframework visual`](/docs/tooling/visual#run-it) needs. The sample design system runs it from a script of its `package.json`:

<!-- prettier-ignore -->
```json [package.json]
    "preview": "unframework preview",
```

It prints the page's URL, then each target's server, and runs until you press `Ctrl+C`, which stops every server. These are its options:

| Option         | What it does                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------- |
| `--target <t>` | Shows one target, and can be repeated. By default it shows every target of your configuration. |
| `--port <n>`   | The page's port. By default the system picks a free one, and each target's server always does. |

It exits `0` once you stop it, and `2` on a usage or configuration error, a project with no example and no component, or a package it needs that isn't installed.

The preview is for your machine while you develop: every server listens on `127.0.0.1` only. Each target's compiler stack, like Angular's, comes from [`package.resolveFrom`](/docs/tooling/configuration#fields), as for `unframework test`.

## What it shows

The page lists your examples first, then your components. An example is a [`*.example.uf.tsx` file](/docs/tooling/visual#examples) with no props, found as `unframework visual` finds it. A component is the default export of a `.uf.tsx` file under `srcDir`, an example excepted. A file with no default export, or one that doesn't compile, isn't listed, and `unframework check` says why.

The page opens on the first example, and keeps the selection in its URL, so a reload or a link shows the same thing. Each frame's caption names its target and says whether it rendered, or why it failed.

A component renders with props alone, so its slots are empty and its models keep their defaults. To see a component with content, write an example that fills it, as `examples/Buttons.example.uf.tsx` does for `Button`.

## Controls

A component gets one control for each prop whose type the preview can set:

| Prop type                  | Control              |
| -------------------------- | -------------------- |
| `boolean`                  | A checkbox           |
| `string`                   | A text field         |
| `number`                   | A number field       |
| A union of string literals | A list of its values |

The type can be an alias, even one imported from another file. The sample design system's `Button` takes a `variant?: ButtonVariant`, from its `src/types.ts`:

<!-- prettier-ignore -->
```ts [src/types.ts]
export type ButtonVariant = "primary" | "secondary";
```

So its `variant` gets a list of `primary` and `secondary`. Change it, and every frame renders the button again with the new value, in place.

An optional prop starts unset, so the component's own default applies, and its control offers "(default)" to go back to it. A blank text or number field leaves an optional prop unset too. A required prop starts at `false`, an empty string, `0` or the first value of its union. A prop of any other type, like a function, an object or a union of numbers, gets no control. The page names it, with its type.

## How it works

Each target gets a Vite dev server of its own, built the way `unframework test` builds a browser project: the Unframework plugin for that target, then the target's own plugins. Each listens on a port of its own, so each frame has an origin of its own, and the frameworks never share a page. The page sends each frame the selection and its props with `postMessage`, and each frame mounts it with that target's mount adapter, the one the tests use. Astro has no client runtime, so its frame asks its own server to render on the server, and inserts the HTML.

The preview writes nothing beside your sources. Vite keeps each server's cache in `node_modules/.vite`, and Angular's compiler keeps its scratch in `.uf-tmp/`, in the directory its stack resolves from.

The first time a target meets a dependency it hasn't bundled yet, Vite bundles it and reloads that frame. The frame then asks for the selection again, so you don't have to do anything.

From a script, `startPreview({ root, targets?, port?, toolchainDirs? })` from `@unframework.dev/visual` starts the same servers. It resolves to `{ url, frames, close }` once every one listens: `url` is the page's, `frames` lists each target's origin and port, and `close()` stops them all. That's how an agent takes a screenshot of the page with Playwright, then stops the preview.
