Unframework compiles each component to eight targets. Each one writes a component in its framework's own format, and imports nothing but its framework and the helper modules in its tree's `_unframework/` directory. `solid@2` is opt-in: a project selects it in `targets`, and the default is the other seven ([Configuration](/docs/tooling/configuration)).

| Target  | File                 | Component                                                   |
| ------- | -------------------- | ----------------------------------------------------------- |
| React   | `ProductTile.tsx`    | A function component                                        |
| Vue     | `ProductTile.vue`    | A single-file component with `<script setup lang="ts">`     |
| Svelte  | `ProductTile.svelte` | A component in runes mode, with `<script lang="ts">`        |
| Angular | `product-tile.ts`    | A component class with signal inputs and an inline template |
| Solid   | `ProductTile.tsx`    | A function component                                        |
| Solid 2 | `ProductTile.tsx`    | A function component, for Solid 2 (`solid@2`)               |
| Qwik    | `ProductTile.tsx`    | A `component$`                                              |
| Astro   | `ProductTile.astro`  | A component with its props in the frontmatter               |

[Props](/docs/components/props) shows the files for one component.

## Capabilities

A capability is a feature a component can use: a kind of node, a kind of attribute, or something a framework does at run time. Each target declares, for every capability, how it supports it:

- **native**: the framework has the feature, and the output uses it;
- **emulated**: the output uses a small helper, named in the cell, because the framework lacks the feature. Most helpers are shared: each is one module in the tree's `_unframework/` directory, which the outputs that use it import. A helper that keeps state for one file, reads a component's own names or is too short to be worth an import is declared in the file instead ([ADR-0121](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0121-helpers-live-in-shared-modules.md));
- **unsupported**: the framework renders the feature differently, or not at all. The compiler reports [UF4001](/docs/reference/diagnostics#UF4001) at the feature's first use, with the target's reason, and the cell sets its severity; `sheet-order` reports its own code, [UF4002](/docs/reference/diagnostics#UF4002), Angular's `child-root-scope` [UF4003](/docs/reference/diagnostics#UF4003), Angular's `generic-slot-props` [UF4004](/docs/reference/diagnostics#UF4004), and React's, Solid's and Solid 2's `composable-effect-order` [UF4005](/docs/reference/diagnostics#UF4005).

So a difference between frameworks is declared here, never found only in a test.

The cells that are not native:

- **React, `class-binding`**: React's `className` takes one string, so a shared helper, `cx`, joins the static names, toggles and dynamic parts. Where a part may be an array or an object at run time, `cx` reads an array's entries too, as Vue's `normalizeClass` does.
- **React, `style-binding`**: React's `style` takes an object, so a `style` bound to a value goes through a shared helper, `styleObject`, which splits a declaration list into an object as Vue's `parseStringStyle` does, with camel-case keys. An object passes as it is. Declarations print as an object.
- **React, `event-once`**: React has no once listener, so a shared guard, `useOnce`, remembers each element the listener ran for, as `{ once: true }` removes a listener from its own element only.
- **React, `event-semantics`**: where React's synthetic event differs from the DOM's (`change` on a text field, a checkbox or a radio, `select`, `beforeinput`, a `wheel` or touch listener that is not passive, the events React has no prop for, and `focus` or `blur` beside a native `focusin` or `focusout`), the element's ref callback, declared once, listens natively, through a shared helper, `listen`.
- **React, `next-tick`**: React has no `nextTick`, so a shared hook, `useNextTick`, asks for a render at the priority of the code that calls it, and resolves once React has rendered it, run its effects and rendered what the component's watchers wrote. After a click's or a key's handler it resolves in the event's task, as on Vue; after a watcher's write, in an effect, in a timer or after an `await`, in a later task ([Semantics](/docs/reference/semantics#outside-the-contract)). It resolves when the component unmounts too.
- **React, `model-array`**: React's checkbox takes one boolean, so a checkbox group's array goes through an inline helper, `toggle`, which adds or removes the box's `value`, as Vue's `vModelCheckbox` does.
- **React, `model-modifiers`**: React has no `v-model` modifiers, so a shared helper, `modelText`, a hook named `useModelText` in the output, trims and casts as Vue's `vModelText` does, and writes a `lazy` field as it loses focus.
- **React, `child-root-scope`**: a child cannot know the scope attributes its styled parents pass it, `data-uf-<id>`, since each name is a parent's id. A root that spreads the props' rest takes them with it. Where the root does not, a shared helper, `scopeAttributes`, picks the `data-uf-*` keys out of the rest of its props and spreads them on it: on each branch of a root conditional, on a root `<component is>`, and on the root of a component that spreads its rest on another element, as Vue's fallthrough reaches them. That element spreads the rest without them, through a second helper, `restAttributes`, declared in the file.
- **React, `reactive-context`**: a context passes its value once per render of the provider, so a provided ref is an object with a `value` getter, `refObject`, made again at each render. Descendants render each change, and code that runs later, after an `await` or in a timer, reads the value of their last render.
- **React, `composable-effect-order`** (for information): a composable is a custom hook, and React runs a component's effects in its own order, so a composable's watchers, effects and hooks cannot take their place among the caller's own, and code that relies on that order may see another. The compiler reports [UF4005](/docs/reference/diagnostics#UF4005) at the composable's call.
- **React, `directive`**: React has no directive, so an element's directive goes through a shared hook, `useDirective`, called once per use at the component's top level. Its ref callback records each element it receives, so a callback written in place keeps the directive and each element one use renders gets its own hooks, and its layout effect runs `mounted`, `updated` when the value changes and `unmounted`. A directive whose value reads a list's row or a scoped fill's props calls `useElementDirective` instead, whose function makes each element's ref callback from its value as the row renders, `withTrace(item.label)`, joined with the element's other callbacks through the shared `mergeRefs`. The hooks go through a shared queue, `queueHook`, which runs them in Vue's order once the turn ends ([ADR-0099](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0099-portable-directives.md), [ADR-0108](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0108-directives-on-rows-and-scoped-fills.md)).
- **React, `transition`**: React has no transition primitive, so a shared component, `Transition`, renders the child, whose branches each take a key. A change of key keeps the old element, as it last rendered, beside the new one until its leave ends. It owns the classes in state, since React writes the whole `class` attribute when `className` changes, keeps the child's own ref, and renders no class on the server or while the client hydrates ([ADR-0100](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0100-transition.md)).
- **React, `async-setup`**: a component can't await in React, so a function of the module, `profileSetup` for `Profile`, runs the awaits, and the component starts it once and renders an inner one, `ProfileResolved`, which reads the result with `use` inside a `<Suspense>`. Its fallback, a shared component, `SetupPending`, renders nothing and tells the component once the setup settles, so React shows the content at once rather than after its fallback throttle. A prop update that arrives while the component hydrates and its setup is pending makes React render it on the client: the server's DOM goes, and nothing shows until the setup resolves, with no mismatch reported. Under `StrictMode` in development the setup runs twice ([ADR-0101](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0101-async-setup.md)).
- **Svelte, `event-once`**: a once listener's handler goes through a shared wrapper, `once`, whose guard is set when the handler first runs, never the DOM's `{ once: true }`: Svelte's `on` runs the handlers it delegated below the element inside its own listener, so the option would be used up by an event one of them stopped.
- **Svelte, `style-binding`**: Svelte's `style` takes a declaration list, so a `style` bound to a value goes through a shared helper, `styleText`, which writes an object's present values as declarations, in kebab case, as Vue's `stringifyStyle` does. A string passes as it is. Declarations print as `style:` directives.
- **Svelte, `fallthrough`**: a component's `style` prop is a string, which cannot unset a property, so a shared helper, `mergeStyle`, merges the consumer's declarations over the root's own and drops the root's declaration of a property the consumer's style sets to a nullish value, as an object merge does. The attributes and listeners a component does not declare are its props' rest, natively: its props type declares its root element's attributes from `svelte/elements` but for its own names, and the root, or the element that spreads the source's `...rest`, spreads the rest last, so the consumer's attribute wins. Where that element listens to an event itself, its handler calls the consumer's listener after its own code. On a root `<component is>` over tags, the props type takes what every tag takes, with the listeners of whichever renders, and the root's own listener that calls the consumer's is checked against the consumer's type with `satisfies`.
- **Svelte, `child-root-scope`**: a child cannot know the scope attributes its styled parents pass it, `data-uf-<id>`, since each name is a parent's id. A root that spreads the props' rest takes them with it. Where the root does not, a shared helper, `scopeAttributes`, picks the `data-uf-*` keys out of its `$props()` and spreads them on it: on each branch of a root conditional, on a root `<component is>`, and on the root of a component whose source spreads `...rest` on another element, as Vue's fallthrough reaches them. That element spreads the rest without them, through a second helper, `restAttributes`, declared in the file. A parent passes them in an object spread, `{...{ "data-uf-<id>": "" }}`, since svelte-check rejects a prop the child does not declare.
- **Svelte, `model-modifiers`**: `bind:value` has no modifiers, so a shared helper, `modelText`, trims, casts and waits for `change` as Vue's `vModelText` does.
- **Svelte, `reactive-context`**: `setContext` passes a value once, so a provided ref is an object with a `value` getter, `refObject`, which descendants read as it changes.
- **Svelte, `teleport`**: Svelte has no portal, so the element renders once the component has mounted, in an `{#if}` of its own, and a shared attachment, `teleport`, moves it into `to`, gives back the focus the move takes, and removes it on teardown. Svelte still delegates its events, since `mount()` listens on `document` too (ADR-0098).
- **Svelte, `transition`**: Svelte's transitions run their own CSS or ticks, never Vue's classes, so each element of the conditional takes a local `in:enter` and `out:leave`, whose shared functions run the classes in a config Svelte calls for every run, and give Svelte the element's duration. A run stops what the element's other phase still runs, as when Svelte reverses a leave. Svelte ends both elements of a swap by that duration, and the classes go then, at `introend` and `outroend`. With `appear`, `in:` is global, so the enter runs as the element first mounts too ([ADR-0100](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0100-transition.md)).
- **Solid, `class-binding`**: Solid's `class` takes one string, so a shared helper, `cx`, joins dynamic parts with the static names and toggles. Static names and toggles alone print as `class` and `classList`. Where a part may be an array or an object at run time, `cx` reads an array's entries too, as Vue's `normalizeClass` does.
- **Solid, `style-binding`**: Solid's `style` takes an object with kebab-case keys, so a `style` bound to a value goes through a shared helper, `styleProperties`, which writes an object's camel-case keys in kebab case and splits a declaration list as Vue's `parseStringStyle` does. Declarations print as an object.
- **Solid, `child-root-scope`**: a child cannot know the scope attributes its styled parents pass it, `data-uf-<id>`, since each name is a parent's id. A root that takes what falls through takes them with it. For any other root, a shared helper, `scopeAttributes`, picks the `data-uf-*` keys out of its props by name and spreads them on it: on each branch of a root conditional, on a root `<component is>`, and on the root of a component that spreads its props' rest on another element, as Vue's fallthrough reaches them. That rest leaves them out through a second helper, `restAttributes`, declared in the file. Neither helper reads a prop's value, so neither runs a getter.
- **Solid, `interactivity`**: state, derived values, listeners and hooks are Solid's own. Solid runs what a write triggers as the write is made, so a watcher goes through an inline helper, `createWatcher`, and a `watchEffect` through `createWatchEffect`, over a scheduler: `createReaction` queues a watcher when a value it read is written, and a microtask runs each queued watcher once, those before the DOM updates first, with Vue's previous value, change test and cleanup timing. Client code is copied as written, with no `batch`: the watchers, not the writes, keep the contract's timing.
- **Solid, `next-tick`**: Solid applies writes to the DOM as it makes them, and the watchers run in a microtask queued at the first write, so a shared `nextTick` resolves a promise.
- **Solid, `model-array`, `model-modifiers` and `reactive-context`**: Solid has no `v-model`, so helpers bind a checkbox group's array (`toggle`), a multiple select's (`selectedValues`), the options of a select that a component, a slot or an interpolation renders (`selectOptions`) and a text field's modifiers (`modelText`), as Vue does. `selectOptions` and `modelText` are shared, and `toggle` and `selectedValues` are declared in the file. A provided ref is an object with a `value` getter, `refObject`, which descendants read as it changes.
- **Solid, `keyed-identity`**: Solid's `<For>` follows the items themselves, so an item replaced by a copy of the same key would get a new element, and lose its focus and typed text. So a list goes through a shared helper over `<For>`, `KeyedFor`, whose rows follow the source's `key`, as Vue's do. A row is an object of getters named as the item, `item.value` and `item.index`, which TypeScript narrows as it narrows a prop, and follows the latest item of its key.
- **Solid, `composable-effect-order`** (for information): a composable's watchers coalesce in its own module's queue, `createWatcher`, apart from the caller's, so its watchers, effects and hooks cannot take their place among the caller's own, and code that relies on that order may see another. The compiler reports [UF4005](/docs/reference/diagnostics#UF4005) at the composable's call.
- **Solid, `teleport`**: Solid's `<Portal>` wraps its content in a `<div>`, so a shared helper, `Teleport`, inserts the element into `to` once the component has mounted, as `<Portal>` does in `<head>`, in a root its owner owns, so the element reads the component's context (ADR-0098).
- **Solid, `transition`**: Solid's own transitions are a package, which no output imports, so a shared component, `Transition`, resolves the child and keeps a leaving element among the nodes it renders until its leave ends. The server renders the child as it is ([ADR-0100](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0100-transition.md)).
- **Solid, `directive`**: a directive is a ref factory, `ref={vFocusTrap(() => open())}`, Solid 2's own form. Solid runs an element's ref before its children's, so the hooks go through a shared queue, `queueHook`, which runs them in Vue's order once the turn ends ([ADR-0099](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0099-portable-directives.md)).
- **Solid 2, `interactivity`**: Solid 2 lets a read see a write only once it flushes, on a microtask or at `flush()`, which an effect's callback or `onSettled` cannot call, and Vue's read sees a write at once. So state goes through a shared helper, `createState`, a signal whose read returns the value last written and tracks the signal where something observes it. A file with watchers declares its own `createState` instead, whose write also asks that file's scheduler to run them. A derived value is a function, `() => count() * 2`, which reads the latest values too. Solid applies what a write changes when it flushes, as Vue renders after a tick. A watcher goes through `createWatcher`, and a `watchEffect` through `createWatchEffect`, over a scheduler queued at the write, which applies Solid's writes and runs each queued watcher once, those before the DOM updates first, with Vue's previous value, change test and cleanup timing. ## Component events

A component declares its events with `defineEmits` ([Events](/docs/components/events#component-events)), and each target takes them in its framework's convention, keeping the event's name, apart from Angular's prefix for the names of DOM events:

| Target  | A parent listens to `change` with | The listener receives                                                                              |
| ------- | --------------------------------- | -------------------------------------------------------------------------------------------------- |
| React   | the prop `onChange`               | the payload's members, as arguments                                                                |
| Vue     | `@change`                         | the payload's members, as arguments                                                                |
| Svelte  | the prop `onchange`               | the payload's members, as arguments                                                                |
| Angular | the output `(ufChange)`           | nothing for an empty payload, the value for one required member, and a tuple for any other payload |
| Solid   | the prop `onChange`               | the payload's members, as arguments                                                                |
| Qwik    | the prop `onChange$`              | the payload's members, as arguments; the listener may run after the emit                           |
| Astro   | nothing                           | nothing: Astro components render on the server only, and emit nothing                              |

Angular's `output()` emits one value, so a payload of two members or more, or with an optional member, is a tuple of exactly the arguments the emit gives: `share: [path: string, note?: string]` emits `["a.txt"]` or `["a.txt", "Please review"]`. React, Solid and Qwik type their event props with an exported interface beside the props, `<Name>Events`, and Svelte joins them to its `Props` type. Angular declares an output for each event under the event's name. An event named like a DOM event, such as `change`, `select` or `progress`, takes the `uf` prefix, `ufChange`, because an Angular output also hears the DOM's event of its name when that bubbles out of the host element: angular-eslint's `no-output-native` rule lists the names. Where a setup binding has that name, the class renames its own member: a local function `save` that emits `save` becomes the method `onSave`, and a state `status` the signal `currentStatus`.

## Development-only code

A component writes `if (isDev) { … }` ([Development-only code](/docs/components/development-only-code)), and each target tests its framework's own development check, which that framework's production build folds to `false` (ADR-0117):

| Target  | `if (isDev)` becomes                                       | A top-level block runs in             |
| ------- | ---------------------------------------------------------- | ------------------------------------- |
| React   | `if (process.env.NODE_ENV !== "production")`               | the component's body, on every render |
| Vue     | `if (process.env.NODE_ENV !== "production")`               | `<script setup>`                      |
| Svelte  | `if (process.env.NODE_ENV !== "production")`               | the instance script                   |
| Solid   | `if (isDev)`, `isDev` imported from `solid-js/web`         | the component's body                  |
| Solid 2 | `if (isDev)`, `isDev` imported from `@solidjs/web`         | the component's body                  |
| Angular | `if (typeof ngDevMode === "undefined" \|\| ngDevMode)`     | `ngOnInit`                            |
| Qwik    | `if (isDev)`, `isDev` imported from `@qwik.dev/core/build` | the `component$` body                 |
| Astro   | `if (import.meta.env.DEV)`                                 | the frontmatter                       |

Vite replaces `process.env.NODE_ENV` only in client code, so a React, Vue or Svelte server reads it as it runs: a production server sets `NODE_ENV=production`, as React and Vue themselves need. Solid 1's server build reads its `isDev` as `false`, so its server render never runs the block. A packaged output keeps each check as written, for the app's build to decide.

## The Angular host

Angular renders every component inside a host element, which wraps the template's root. The other frameworks render the root directly. Unframework gives each Angular component an element selector, `uf-` and its name in kebab case, and styles its host `display: contents`:

<!-- prettier-ignore -->
```ts [product-tile.ts]
@Component({
  selector: "uf-product-tile",
  host: { "[attr.class]": "null", "[attr.style]": "'display: contents;'" },
  preserveWhitespaces: false,
```

A consumer writes `<uf-product-tile>`, Angular's ordinary element syntax. `display: contents` keeps the host out of layout, so the component's geometry and pixels match the other targets'. Its accessibility tree differs in one place: Playwright's ARIA snapshot puts a space at every element whose `display` isn't `inline`, the host included, so inline content on either side of a host reads "Build passing" where the other targets read "Buildpassing". The parity tests take Angular's snapshot with its hosts set to `display: inline`, so they add no space ([ADR-0060](https://github.com/uxfront-com/unframework/blob/main/docs/adrs/0060-react-bound-controls-and-angular-host-spaces.md)). The template holds the whole render tree: a single root, the roots of a root fragment, and the conditionals and lists beside them all render inside the one host.

The host keeps nothing a consumer writes on it: `[attr.class]` and `[attr.style]` clear any `class` and `style` there, apart from its own `display: contents`. A consumer's `class` and `style` reach the component's root element through two inputs instead, and the other attributes and native listeners it passes through two more, `ufAttributes` and `ufListeners`, which a shared directive, `Fallthrough`, puts on the root ([Fallthrough](/docs/components/fallthrough)). A static prop is bound, `[label]="'Name'"`, so that no attribute stays on the host.

So a hand-written Angular consumer binds what it passes too: `id="save"` on `<uf-save-button>` would stay on the host, and `[ufAttributes]="{ id: 'save' }"` puts it on the button. Keep the record's keys fixed, and pass `null` for an attribute to remove: a key the record drops removes its attribute, and the root's own static value of it doesn't come back, where Vue's would. The host is no element a ref may hold either, so a component that exposes nothing declares `ufElement`, its root element, which a ref on it reads ([Expose and component refs](/docs/components/expose-and-refs#a-ref-on-a-component-that-exposes-nothing)).

Attribute selectors, which would make the consumer's own element the host, are left to a decision of their own, outside M3. Until they land, a component whose root must sit directly inside its parent, such as an `<li>` in a consumer's list or a `<tr>` in a consumer's table, cannot be written for Angular ([`contextual-root`](#capabilities), an error): keep that element in the parent, and render the component inside it ([Child components](/docs/components/child-components#in-lists-and-conditionals)).
